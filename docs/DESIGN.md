# 3D試着室（仮称）— 設計書

- 状態: MVP 実装済み（2026-11-20）
- 正式名称: **未決定（mi の判断事項）**。本書とアプリ内では仮称「3D試着室 / 3D Fitting Room」を使う。
- 作業場所: `~/workspace/fitting-room/`（ローカル git のみ。GitHub リポジトリ作成・公開は mi の判断待ち）

## 1. 目的

アバターに服や小物を着せ替えて遊ぶ 3D アプリ。目的はニコニコ動画や
淫夢文化のような **「公開と認知」そのもの** — 利用者が着せ替えた姿を
画像にして持ち帰り、どこかで見せびらかして面白がってもらうこと。
売るものでも、集金するものでもない。

だから中核機能は着せ替えそのものより **「ワンタップで共有カード PNG を
書き出せること」** に置く。カードにはアプリ名が入り、画像が広がるほど
アプリの存在が広がる。それ以外の拡散装置（SNS 連携 API、共有 URL、
サーバー側ギャラリー等）は持たない。画像ファイル自体が媒体になる。

## 2. 設計不変条件（破ったら製品でなくなるもの）

### 2.1 金を一切絡ませない
- 広告なし、課金なし、サブスクなし、投げ銭・寄付の導線も製品内に入れない。
- 「将来収益化するためのフック」も作らない。決済・寄付・広告・サブスクの
  仕組みが **未使用のコードとしてすら存在しない** ことを
  `tests/invariants.test.ts` が文字列レベルで固定している。
- 運営コストもゼロに寄せる: バックエンドを持たないので、置き場所は
  静的ファイルの配信だけで済む（誰がどこに置いてもよい）。

### 2.2 作成者は個人データを持たない（全プロダクト共通の大原則）
- バックエンドなし、アカウントなし、解析・テレメトリなし。
- コーデの保存先は利用者端末の localStorage のみ。
- ネットワーク接続は原則ゼロ。唯一の例外は、利用者が自分で設定した
  LLM エンドポイントへの接続（§13。2026-11-20 に mi の明示指示で
  追加）。製品にエンドポイントは同梱されず、利用者が設定するまで
  一切接続しない。送信されるのは指示文と現在の状態パラメータのみ、
  送信先は利用者のエンドポイントだけである。この例外の範囲は
  `tests/invariants.test.ts` が固定している: ハードコードされた
  非ループバック URL の禁止、ネットワーク呼び出しは `src/llm.ts`
  の1モジュールと Service Worker（同一オリジンのオフライン
  キャッシュ専用、ガード条件もテストで固定）に限定。
- 書き出した PNG は端末内で合成され、端末のダウンロードとして落ちるだけ。

### 2.3 素材は権利の綺麗なものだけ
- 著作権キャラクター・権利不明の素材は使わない。
- アバターもアイテムも全てコードで組み立てる（Three.js プリミティブ）。
  テクスチャ画像・外部モデル・外部フォントはゼロ。台帳は §7。

## 3. 形態の判断

**Three.js + Vite + TypeScript の Web アプリを、インストール可能な PWA として作る。**

- スマホ・PC の両方でそのまま動き、「ホーム画面に追加」でアプリとして
  インストールできる。ストア審査もストア手数料も介在しない（＝金を
  絡ませない条件と相性がよい）。
- リポジトリ公開物はソフトウェアとして作るという方針に沿う形
  （ビルド成果物＋マニフェスト＋Service Worker のアプリ一式であり、
  単なる Web ページではない）。
- 代替案の却下理由:
  - ネイティブ（Capacitor 等）: 配布にストアが必須になり、金と審査の
    入口が増える。MVP の学び（見た目・着せ替え・書き出し）には不要。
  - 単一 HTML: 公開物の形態として認めない方針に反する。
- UI は日本語＋英語の i18n を最初から実装（辞書のキー一致をテストで固定）。

## 4. アーキテクチャ

ビルド成果物は静的ファイルのみ（`dist/`）。実行時の外部通信はゼロ。

| ファイル | 役割 |
|---|---|
| `src/main.ts` | 起動・UI 配線・状態の単一の更新経路（update → 適用＋端末内保存） |
| `src/avatar.ts` | ベースアバター（パラメータ駆動の生成、ポーズ補間、まばたき、アンカー群） |
| `src/character.ts` | キャラクターパラメータの正本（仕様・検証・肌色変換） |
| `src/seed.ts` | 人物＋コーデ全体のシード符号化／復号 |
| `src/items.ts` | アイテム生成と着せ替え適用（トップス／帽子／メガネ／小物） |
| `src/scene.ts` | レンダラ・ステージ・ライト・OrbitControls、身長への追従 |
| `src/outfit.ts` | コーデの型・検証・localStorage 保存／復元・ランダム生成 |
| `src/share.ts` | 共有カード PNG の合成とダウンロード |
| `src/i18n.ts` | 日英辞書と `t()` |
| `public/sw.js` | オフライン用アプリシェル（同一オリジン限定キャッシュ） |
| `tools/verify.cjs` | 本番ビルドのヘッドレス実走検証（Electron） |
| `tools/verify-character.cjs` | キャラクター生成（フェーズ0+1）のヘッドレス実走検証 |
| `tools/make_icons.py` | アイコンの手続き的生成（PIL） |

検証用に `window.__fittingRoom` ブリッジ（状態取得・設定・カード生成）を
公開している。利用者のデータではなくアプリ状態の読み書きのみ。

## 5. MVP 範囲（実装済み）

1. **ベースアバター 1 体**: 外部モデルなし、プリミティブ＋フラット
   シェーディングのローポリ調ちびキャラ。髪・顔（目・ほっぺ・口）まで
   コード生成。
2. **試着（カテゴリ 4 つ）**:
   - トップス: Tシャツ／パーカー／ワンピース × 色 7 色（袖も連動）
   - 帽子: なし／キャップ／ニット帽／ねこ耳／リボン
   - メガネ: なし／まる／しかく／サングラス
   - アクセサリー: なし／ネックレス／マフラー／バッグ
3. **カメラ・ポーズ・表情**: ドラッグ回転・ズーム（OrbitControls）、
   自動回転、視点リセット。ポーズ 5 種（ふつう／てをふる（アニメ付き）／
   バンザイ／ピース／リラックス）、表情 5 種（ふつう／にっこり／
   ウィンク／びっくり／ねむい）。
4. **共有カード書き出し（中核機能）**: 1080×1080 PNG。現在の姿を
   正方形に切り抜き、アプリ名＋タグラインを入れてダウンロード。
5. **コーデ保存**: localStorage に自動保存し、次回起動時に復元。
6. **その他**: ランダムコーデ、PWA（マニフェスト＋アイコン＋
   オフラインシェル）、レスポンシブ（スマホは下部シート、広画面は右パネル）。

非目標（MVP ではやらない）: 体型・髪型の変更、複数アバター、アイテムの
追加ダウンロード、SNS 直接投稿、共有 URL、オンラインギャラリー、
アニメーション付きポーズの拡充。

## 9. 品質引き上げ記録（2026-11-20、mi 指示「GTA6に品質を近づける。リアル寄り」）

### 9.1 変えたこと

- **アバター全面作り替え**: ローポリちびキャラ（約3頭身）→ 約7.2頭身・
  身長 1.74m のリアル寄りプロポーション。胴体・頭部は Lathe＋スプライン
  プロファイルの滑らかな形状にし、頭部は実頭比率（横 0.88／奥行 1.12）に
  変形。目・まぶた・眉・鼻・唇・耳を頭部表面に沿って配置。髪は頭蓋追従の
  シェル＋前髪＋後ろ髪＋サイドロックのボブ形状。自動まばたき（約3.6秒
  周期）と呼吸・重心の微小な揺れで「置物感」を消した。
- **質感**: PBR マテリアル化（肌 roughness 0.58、髪 0.38、布はアイテム
  側）。テクスチャは全て Canvas 手続き生成（`src/textures.ts`）:
  布の織り目（カラー＋bump）、肌、髪のストランド bump、木目床、漆喰壁、
  レザー、リブ編み bump。乱数はシード固定で再現性あり。外部素材は不使用。
- **服の作り替え**: トップス3種は胴体プロファイル追従の Lathe 形状
  （Tシャツ／フーディ／ワンピース、布テクスチャ、色違い維持）。帽子は
  頭蓋中心基準のドーム形状（キャップ／ビーニー／ねこ耳／リボン）。メガネは
  細い金属フレーム＋透明レンズ。ネックレスは胸の曲面に沿うチューブ形状
  （従来の「埋没」欠陥を回避）。バッグはレザーテクスチャ＋クロスボディ
  ストラップ。
- **空間**: パステルのデコ部屋→高級ブティックの試着室。木床
  （MeshPhysicalMaterial＋クリアコート）、漆喰壁＋パネルモールディング、
  真鍮フレーム付きの**実反射ミラー**（Reflector、1024px）、真鍮インレイ
  付き円形台座、衣類ラック（吊り服3点）、観葉植物、壁面スコーンス×2
  （鏡の反射先として正面壁を新設し、反射に映る光源にした）。
- **ライティング／描画**: ACES Filmic トーンマッピング、RoomEnvironment
  の PMREM 環境光（environmentIntensity 0.45）、PCFSoft シャドウ、
  キー／リムのスポットライト＋方向光フィル＋半球光。ポストプロセス
  （SSAO／Bloom）はモバイル負荷と共有カード書き出し経路の単純さを
  優先して見送り（この判断は 9.3 にも明記）。
- **UI パレット**: ピンク基調→真鍮×暖色ニュートラルのブティック調に
  統一（CSS 変数、共有カード背景、theme-color）。

### 9.2 設計判断: 表情セレクタの廃止

ユーザー選択式の表情（5種）は廃止し、ニュートラルなマネキン顔＋自動
まばたきに変更した。理由: リアル寄りの顔で「目を潰す／口を記号化する」
式の表情切替は即座に破綻し、不気味の谷に入る。実在の試着マネキンの
ように表情を持たない顔の方が、リアル寄りの方向では破綻がない。ポーズ
（5種）は維持。旧セーブデータの `expression` キーは読み込み時に無視
されるため互換性は保たれる（テストで固定）。

### 9.4 GTA6 との差 — 正直な棚卸し

本節は誇張を避けるための記録である。本作は「リアル寄りのマネキン試着」
であり、GTA6 本編の実写級表現とは別物である。届かない理由は技術不足
ではなく制作体制と制約の差である:

- **アセット制作体制**: GTA6 級は数千人規模・数年のモーション
  キャプチャ、フェイシャルリグ、スキャン素材、専任のライティング／
  テクスチャアーティストが前提。本作は単一のブラウザアプリで、
  全形状・全テクスチャがコード生成のみ（外部素材ゼロの不変条件）。
  顔は意図的にマネキン化しており、実在人物の表情演技は対象外。
- **描画**: 実機 GPU 前提の専用エンジンに対し、本作は WebGL
  （Three.js）の範囲。実反射は平面ミラー1枚のみで、SSAO／Bloom 等の
  ポストプロセスはモバイル破綻回避のため未投入。布の揺れ・髪の物理
  シミュレーションはない（静的形状＋ポーズのみ）。
- **アニメーション**: ポーズは関節角度の静的指定＋小さな揺れと
  まばたきのみ。歩行・着替え動作のような全身モーションはない。
- **未検証**: 実機スマホでの描画負荷・発熱・バッテリー消費、実機
  GPU でのフレームレートは未測定（検証は VM 上のソフトウェア
  レンダリングのみ）。実ブラウザ（Chrome／Safari）表示、PWA
  インストール、オフライン再訪も MVP 時点から引き続き未検証。
- **到達点の自己評価**: 「デフォルメちびキャラ」から「実寸プロポー
  ション＋PBR 質感＋実反射のあるブティック空間」へは移行できた。
  写真と見紛う水準ではなく、質の良いマネキン人形の試着体験が正確な
  表現である。

## 10. キャラクター生成システム フェーズ0+1 実施記録（2026-11-20）

設計正本は `docs/CHARACTER-SYSTEM.md`（全6フェーズ）。本節はその
フェーズ0（基盤）とフェーズ1（効く核）の実施記録である。

### 10.1 フェーズ0: パラメータ基盤

- **パラメータベクトルの正本**: `src/character.ts` の
  `CHARACTER_PARAM_SPECS` が唯一の定義。パラメータは5件 —
  肌色（連続 0..1）、身長（1.45〜1.95m）、髪色（パレット8色）、
  瞳色（パレット6色）、髪型（5種）。範囲・選択肢・既定値はここ
  だけが決め、検証（sanitize）と UI とシード符号化は全てここから
  導くので、定義がずれようがない構造にした。
- **保存形式**: `Outfit` に `character` を埋め込んだ。保存キー
  （`fitting-room.outfit.v1`）は据え置きで、旧セーブ（character
  キーを持たない）は既定値で補完されてそのまま読めることを
  テストで固定した。
- **シード符号化**: `src/seed.ts`。人物＋コーデ全体を12バイトの
  固定順配列（版数先頭、連続値は量子化: 肌色 1/255・身長 1cm）
  にし、base64url＋接頭辞 `FR1-` の19文字にした。復号→再符号化
  が完全一致することをテストで固定。人物タブに表示・コピー・
  貼り付け適用の UI を置き、検証ブリッジにも getSeed/setSeed を
  追加した。受け取り側は端末内で再現するだけで、サーバは要らない
  （CHARACTER-SYSTEM.md §2.5 の形の最小実装）。

### 10.2 フェーズ1: 効く核

- **色のパラメータ化**: 肌色はフィッツパトリック I〜VI の代表色
  アンカー間を区分線形補間して肌マテリアルの色にする。肌テクス
  チャは近白で色が乗算されるため、質感は全トーンで保たれる。
  既定値 0.28 は旧固定色 `#e9b48c` と各チャンネル ±8 以内で、
  既定の人物の見た目が変わらないことをテストで固定した。髪色は
  髪マテリアル（眉も連動）、瞳色は目マテリアルへ反映。
- **身長スライダー**: アバター生成がパラメータ駆動になり、身長は
  生成時のフレームスケール（縦は身長比そのまま、横は変化量の
  45% に減衰 — 背だけ伸びて横は控えめ）で再生成される。カメラの
  ホーム位置・注視点と、ミラーのガラス＋枠の再レイアウトが
  `stage.setSubjectHeight()` で追従する。
- **ポーズ遷移の補間**: `applyPose` は目標角度の設定だけにし、
  `tick` が指数減衰（係数 1−exp(−7·dt)、dt は 0.05s でクランプ）
  で現在角度を目標へ寄せる。瞬間移動は消えた。wave の腕の振りは
  目標側へ加算する形に移した。
- **まばたきの自然化**: 固定 3.6 秒周期を廃止。間隔は 2.1〜5.7 秒
  のランダム（16% の確率で 0.3 秒後の二度瞬き）、開閉は「速く
  閉じる（38%）→一拍保持→ゆっくり開く（48%）」のスムーズステッ
  プ曲線。両目は同一曲線で同期する（実物の瞬きと同じ）。スケ
  ジュールはシード固定 LCG で、検証の再現性を保った。
- **髪型の追加**: ボブに加えてロング／ショート／ポニーテール／
  お団子の4種。全て頭蓋追従シェル＋手続き形状で、髪色パラメータ
  がそのまま乗る。

## 13. LLM 接続 実施記録（2026-11-20、mi 指示「自分で LLM を持ってる場合、接続できて操作できる仕組みを追加。エージェントなど」）

### 13.1 実装したもの

- **接続設定 UI**（新タブ「AI接続」）: エンドポイント URL

「作成者は個人データを持たない」原則は維持される: 開発者側に
送られるデータは存在せず、送信は利用者自身のエンドポイント
へのみ、送信内容は指示文と現在の状態パラメータのみである。

### 13.3 セキュリティレビュー

- **LLM 出力は信用しない**（最重要）: 応答は JSON として解析し、
  コマンドは全てホワイトリスト方式で検証する。範囲パラメータは
  仕様範囲にクランプ、選択式は選択肢外を拒否、未知のコマンド・
  未知のパラメータは実行しない。適用結果は通常の保存データと
  同じ `sanitizeOutfit` を必ず通るため、法律・倫理層
  （LEGAL-ETHICS.md）の安全制限（パラメータ仕様側に実装）は
  LLM 経由でも回避できない。コード実行・DOM 注入の経路は
  存在しない（コマンドは型付きデータとしてのみ解釈され、
  チャット表示は textContent で行う）。
- **APIキーの扱い**: localStorage にのみ保存し、送信は設定した
  エンドポイントへの Authorization ヘッダのみ。ログ・画面への
  表示はしない（入力欄は password 形式）。
- **プロンプトインジェクションの射程**: 悪意あるモデル応答が
  できることは「検証済みコマンドの範囲で見た目を変える」まで
  であり、それは利用者自身がスライダーでできる範囲と同一。
  それ以外の能力（外部送信先の追加、ファイル操作等）は
  プロトコルに存在しない。
- **エンドポイント URL の検証**: http(s) の絶対 URL のみ許可し、
  それ以外のスキームは接続テスト・送信の前に拒否する。
- **残リスク**: 利用者が悪意あるエンドポイントを自ら設定した
  場合、指示文と状態パラメータがそこへ送られる。これは
  「自分の LLM を接続する」という機能の本質であり、AI接続
  タブ内の注記と LLM-CONNECT.md §3 で送信内容を明示して担保
  する。HTTPS で配信されたアプリから http のローカルサーバへの
  接続はブラウザ側の制限を受ける場合がある（LLM-CONNECT.md
  §2.1 に明記）。

## 15. 体型パラメータ＋成人の安全制限（CUS-0779）実施記録（2026-11-20）

CHARACTER-SYSTEM.md §5.8 の監査後優先順位の第4位（旧フェーズ3
の縮小版）。法律・倫理ゲート **G3** の対象であり、体型の可変化
と安全制限は分離不可の同一単位として実装した（J-02: 生成は
成人＝外見年齢20歳相当〜のみ。CUS-0779 は体型スライダーと同一
フェーズの必須受け入れ条件）。

### 15.1 体型パラメータの選定（監査による絞り込み）

候補は肩幅・ウエスト・ヒップ・体格・筋肉量・バストの6件。
顔と同じ基準（共有画像で「その人らしさ」として読め、現行の
プロファイル／カプセル構成で独立に表現できるものだけを残す）
で監査し、**5件**を採用した:

| パラメータ | 範囲（既定1） | 担う部位 |
|---|---|---|
| 肩幅 shoulderWidth | 0.88–1.14 | 肩関節の配置 |
| ウエスト waist | 0.82–1.22 | 胴プロファイル（ウエスト帯） |
| ヒップ hip | 0.86–1.20 | 胴下部・骨盤・スカート線 |
| バスト bust | 0.80–1.30 | 胴プロファイル（胸部帯） |
| 体格 build | 0.85–1.20 | 胴・脚・腕・首の全体の太さ |

- **削った候補: 筋肉量（独立軸としては不採用）**。滑らかな
  Lathe／カプセル形状では筋肉の「定義」（表面の凹凸）は表現
  できず、この忠実度では筋肉量は周径としてしか読めない。
  体格（build）に吸収した。
- J-04 準拠: 「性別」ラベルは置かない。バストは着衣シルエット
  の範囲（胸部高さのプロファイル半径）だけを担い、解剖学的な
  詳細形状は作らない。UI ラベルは形状名のみ（日英）。

### 15.2 自動フィット

- 体と衣服は同じ Lathe プロファイル方式であり、係数の正本を
  `character.ts` の `bodyRadiusFactor(y, c)`（高さ帯ごとの
  重み付き半径倍率）と `legGirthFactor(c)` に一本化した。
  アバターの胴・骨盤・脚と、衣服のトップス／ドレス／ヒップ
  ブロック／スカート／パンツ脚部が**同じ関数**を通るため、
  体型が変われば衣服は新しい体に縫い直される（これが本単位の
  自動フィット）。既定パラメータでは係数は全高さで正確に1で、
  従来の体型・衣服は不変。
- 体側の再生成は頭部（髪）と同じパターン: 体パラメータが
  変わったときだけ胴・骨盤・脚のグループを再構築し、腕は
  肩位置と太さを追従させる。足の位置（x=±0.096）は体型で
  動かさない（ヒップは骨盤と太ももを広げるだけ）ため、靴は
  常に足に合う。
- 付随調整: フーディのポケットとドレスのウエストバンドは
  その高さの係数で押し出し／拡縮し、ネックレスの垂れは
  バストに連動させた（大きな体格で小物が埋没しないため）。

### 15.3 安全制限 CUS-0779 の設計（J-02 の実装）

2層で構造的に担保する:

1. **動かせない不変量**: 頭の大きさはパラメータではなく、
   身長のフレーム拡縮は全身一様なので、頭身比（約7.2頭身）
   は全パラメータ域で不変。身長下限 1.45m は成人の範囲。
2. **組合せルール**: 単独の特徴は未成年らしさを作らない
   （低身長の成人・平らな胸の成人・直線的な体型の成人は
   実在する）ため、個別範囲は制限しない。未成年に見えるのは
   「低身長＋未発達なバスト＋ウエストとヒップの差がない直線
   ＋細い体格＋狭い肩」が**重なったとき**だけである。
   `youthScore()` がこの重なりを重み付きで数値化し（身長
   0.30／バスト 0.25／直線度 0.20／体格 0.15／肩 0.10）、
   0.5 を超えたら sanitize が組合せを成人の側へ補正する。
   補正はレバー順（バスト→ヒップとウエストの差→体格→肩）
   に、必要な分だけ成人基準値方向へ動かす決定的な処理で、
   **身長は決して補正しない**（低身長は正当な成人の特徴で
   あり、他のレバーの容量合計 0.70 が最大超過分 0.50 を
   常に上回る）。到達不能な場合の最終保証として既定体型への
   フォールバックも置いた（仕様範囲では到達しない）。
- **チョークポイント**: 補正は `sanitizeCharacter` の中で
  効く。保存データ・シード復号・LLM／エージェントのコマンド
  実行は従来どおり sanitize を通る。あわせて今回、UI の
  スライダー経路（`patchCharacter`）とブリッジ経由の状態
  適用（`update`）も sanitize を通すよう揃えたため、**全経路
  が単一の関所を通る**。補正は sanitize 済みの状態そのものに
  残るので、スライダー表示・シード文字列・LLM の適用後状態
  のいずれでも観測可能（黙って通すことはない）。
- テストで固定した代表例: 全信号が極端な組合せ（身長1.45／
  バスト0.80／ウエスト1.22／ヒップ0.86／体格0.85／肩0.88、
  スコア1.0）は、バストとヒップが引き上げられ身長は保持
  された形でのみ存在できる。単独の若年方向の値（低身長のみ
  等）は補正されないことも対で固定した。
